# 04 이벤트 명세 (Redis Streams)

스트림 `orders.events`. 필드는 평탄한 문자열 쌍이다(Streams 제약). payload는 JSON 문자열 하나로 싣는다.

## 메시지 필드

| 필드 | 값 | 뜻 |
|---|---|---|
| event_id | outbox.id (정수 문자열) | 멱등 키. DynamoDB sk에 들어간다 |
| event_type | `order.confirmed`, `order.canceled` | |
| schema_version | `1` | 필드가 바뀌면 올린다. 소비자는 모르는 버전을 DLQ로 |
| occurred_at | ISO 8601 UTC 밀리초 | order_ledger.occurred_at |
| aggregate_type | `order` | |
| aggregate_id | order id | |
| payload | JSON 문자열 | 아래 |

## payload v1

```json
{
  "orderId": "uuid",
  "dropId": "uuid",
  "dropName": "한정판 A",
  "userId": "uuid",
  "quantity": 1,
  "status": "CONFIRMED",
  "confirmedAt": "2026-10-20T10:00:00.123Z",
  "canceledAt": null
}
```

order.canceled는 status CANCELED, canceledAt 채움. dropName을 싣는 이유는 알림 서비스가 주문 서비스를 조회하지 않기 위해서다(경계 규칙).

## 생산 규칙

- 주문 확정과 취소 트랜잭션 안에서 outbox에 PENDING으로 INSERT. 트랜잭션이 롤백되면 이벤트도 없다
- 릴레이가 500ms마다 PENDING 100건을 FOR UPDATE SKIP LOCKED로 잡아 XADD 뒤 PUBLISHED로 갱신. 10회 실패 시 FAILED와 경보
- 순서: 같은 주문의 confirmed와 canceled는 outbox id 순서로 발행된다. 스트림은 단일이라 전체 순서가 유지된다. 소비자가 여럿이라 처리 순서는 보장하지 않는다. canceled가 confirmed보다 먼저 처리돼도 알림 두 건이 각자 저장되므로 문제 없다(알림은 상태 머지가 아니라 사건 기록)

## 소비 규칙

- 그룹 `notification`, COUNT 100, BLOCK 2000
- 성공 또는 조건부 쓰기 실패(이미 있음)는 XACK
- 예외는 ACK 안 함. 같은 소비자가 재시도. idle 30초 넘은 pending은 다른 파드가 XCLAIM
- delivery count 4회째는 `orders.events.dlq`에 원본 필드 + `error`, `failed_at`, `consumer`를 XADD 뒤 XACK
- 모르는 schema_version도 DLQ

## 측정

주문 1만 건 뒤 `XLEN orders.events` = 1만, DynamoDB 건수 = 1만, DLQ 0. 소비자 파드를 처리 중에 죽인 뒤 재개했을 때 DynamoDB 건수 = 1만 유지, pending 0까지 걸린 초.
