# 04 이벤트 명세 (Redis Streams)

스트림 `orders.events`. 필드는 평탄한 문자열 쌍이다(Streams 제약). payload는 JSON 문자열 하나로 싣는다.

## 메시지 필드

| 필드 | 값 | 뜻 |
|---|---|---|
| event_id | outbox.id (정수 문자열) | 멱등 키. DynamoDB sk에 들어간다 |
| event_type | `order.confirmed`, `order.canceled` | |
| schema_version | `1` | 필드가 바뀌면 올린다. 소비자는 모르는 버전을 DLQ로 |
| occurred_at | ISO 8601 UTC 밀리초 | order.confirmed는 payload.confirmedAt, order.canceled는 payload.canceledAt. order_ledger.occurred_at과 같은 값 |
| aggregate_type | `order` | |
| aggregate_id | order id | |
| payload | JSON 문자열 | 아래 |

## payload v1

```json
{
  "orderId": "uuid",
  "dropId": "uuid",
  "dropName": "한정판 A",
  "userId": "uuid",
  "quantity": 1,
  "status": "CONFIRMED",
  "confirmedAt": "2026-10-20T10:00:00.123Z",
  "canceledAt": null
}
```

order.canceled는 status CANCELED, canceledAt 채움. dropName을 싣는 이유는 알림 서비스가 주문 서비스를 조회하지 않기 위해서다(경계 규칙).

## 생산 규칙

- 주문 확정과 취소 트랜잭션 안에서 outbox에 PENDING으로 INSERT. 트랜잭션이 롤백되면 이벤트도 없다
- 릴레이가 500ms마다 PENDING 100건을 FOR UPDATE SKIP LOCKED로 잡아 XADD 뒤 PUBLISHED로 갱신. XADD는 MAXLEN 근사 트리밍 1,000,000
- Redis 연결 실패나 타임아웃이면 attempts를 올리지 않고 그 틱의 남은 행을 건너뛴다. 이미 발행한 행의 PUBLISHED는 커밋하고, 건너뛴 행은 잠금이 풀려 다음 틱에 다시 잡힌다. 전체 롤백은 이미 발행한 행을 재발행하게 한다
- 그 밖의 실패만 attempts를 올리고 10회째에 FAILED, `dropgate_outbox_failed_total`, error 로그를 남긴다. 500ms 틱에서 Redis 장애까지 세면 Sentinel 절체 설계 구간(5에서 15초) 안에 정상 이벤트가 FAILED가 될 수 있다
- 같은 주문의 confirmed와 canceled를 포함해 발행 순서와 소비 순서를 보장하지 않는다. 여러 릴레이가 SKIP LOCKED로 먼저 잠긴 행을 건너뛸 수 있고 소비자도 여럿이다. canceled가 confirmed보다 먼저 발행되거나 처리돼도 event_id별로 알림을 멱등 저장하므로 문제 없다(알림은 상태 머지가 아니라 사건 기록)

## 소비 규칙

- 그룹 `notification`, COUNT 100, BLOCK 2000
- 성공 또는 조건부 쓰기 실패(이미 있음)는 XACK
- 예외는 ACK 안 함. 같은 소비자가 재시도. idle 30초 넘은 pending은 다른 파드가 XCLAIM
- delivery count 4회째는 `orders.events.dlq`에 원본 필드 + `error`, `failed_at`, `consumer`를 XADD 뒤 XACK
- 모르는 schema_version도 DLQ

## 측정

주문 1만 건 뒤 `XLEN orders.events` = 1만, DynamoDB 건수 = 1만, DLQ 0. 소비자 파드를 처리 중에 죽인 뒤 재개했을 때 DynamoDB 건수 = 1만 유지, pending 0까지 걸린 초.
