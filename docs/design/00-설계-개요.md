# dropgate 설계 개요

기준일 2026-10-04. 기술 실험용 B2C 한정판 드롭 플랫폼. 플랜과 측정 계획은 `docs/plan.md`. 이 폴더가 최종 설계의 정본이고, 구현은 이 설계를 따른다. 설계를 바꿔야 하면 코드가 아니라 이 문서를 먼저 고치고 ADR에 이유를 남긴다.

## 1. 방식

슬라이스 방식이 아니다. ERD, Redis 키, DynamoDB, 이벤트, API 명세, 배치, 배포까지 먼저 확정하고 주차 계획대로 구현한다. 이유는 둘이다. 서비스가 셋이라 경계와 계약을 먼저 고정하지 않으면 주차마다 되돌아가고, 측정 질문이 설계에 묶여 있어 설계가 흔들리면 수치를 비교할 수 없다.

## 2. 사용자와 운영자가 하는 일

사용자: 카카오로 로그인한다. 열려 있는 드롭을 본다. 드롭 대기열에 들어가 순번을 본다. 입장되면 60초 안에 구매한다. 1인 1개. 주문을 취소할 수 있다. 내 주문과 내 알림 피드를 본다.

운영자: 드롭을 등록한다(이름, 수량, 오픈과 마감 시각, 초당 입장 인원). 일별 결산과 대조 결과를 받는다.

결제는 없다. 주문 확정이 끝이다.

## 3. 서비스 경계

| 서비스 | 책임 | 저장소 | 포트 |
|---|---|---|---|
| auth-service | 카카오 OAuth2, 사용자 저장, JWT RS256 발급과 재발급, 로그아웃 무효화, JWKS 제공 | PostgreSQL auth 스키마, Redis(리프레시, 무효화) | 8081 |
| order-service | 드롭 등록과 조회, 접속 대기열과 입장, 구매(재고 차감), 주문 확정과 취소, 내 주문 조회, outbox 릴레이 | PostgreSQL orders 스키마, Redis(대기열, 재고, 입장, Streams 발행) | 8082 |
| notification-service | Streams 소비, 알림 피드 저장과 조회 | DynamoDB notifications, Redis(Streams 소비, DLQ) | 8083 |
| settlement-batch | 일별 결산, Redis 대 DB 대조 | PostgreSQL settlement 스키마(Spring Batch 메타 포함), Redis 읽기 | 8084 |

경계 규칙
- 서비스는 다른 서비스의 스키마를 읽지 않는다. PostgreSQL 인스턴스는 하나지만 스키마를 나누고 DB 사용자를 서비스마다 둬 교차 접근을 권한으로 막는다. 결산 배치만 orders 스키마를 읽기 전용으로 본다(배치는 주문 서비스의 소유로 본다).
- 서비스 사이 동기 호출은 없다. 사용자 식별은 JWT 안의 sub로 끝낸다. 드롭 이름처럼 알림에 필요한 값은 이벤트에 실어 보낸다.
- 유일한 비동기 경계는 주문에서 알림으로 가는 Redis Streams다.

## 4. 모듈 구조 (Gradle Kotlin DSL 멀티모듈)

```
dropgate/
  settings.gradle.kts
  build.gradle.kts
  common/              오류 응답, JWT 검증 필터, 이벤트 스키마, 시각 유틸
  auth-service/
  order-service/
  notification-service/
  settlement-batch/
  deploy/
    compose/           로컬: PostgreSQL, Redis Sentinel 3+1+2, DynamoDB Local
    helm/dropgate/     차트 하나, values-kind.yaml, values-eks.yaml
    terraform/         VPC, EKS, RDS, ElastiCache, DynamoDB, ECR, IAM
  docs/adr/
  load/                k6 스크립트, 합성 데이터 적재
```

서비스 안 패키지는 미터엔진과 같이 controller, service, repository, entity, dto, event로 둔다. 헥사고날은 쓰지 않는다. 서비스가 작아 이득이 없다.

## 6. 전체 흐름 한 장

```
사용자 -> Ingress -> auth-service      카카오 로그인, JWT
사용자 -> Ingress -> order-service     대기열 진입 -> 순번 폴링 -> 입장 -> 구매(Lua) -> 주문 확정(DB) -> outbox
                     order-service 릴레이 -> Redis Streams orders.events
                     notification-service 소비 -> DynamoDB notifications
사용자 -> Ingress -> notification-service  내 피드 조회
CronJob -> settlement-batch            일별 결산(orders 읽기 -> settlement 쓰기), 대조(Redis 대 DB)
```
