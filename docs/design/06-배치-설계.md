# 06 배치 설계 (settlement-batch, Spring Batch)

잡 둘. 둘 다 CronJob이 HTTP로 호출하고(07 문서), JobRepository는 settlement 스키마의 Spring Batch 메타 테이블이다. 재시작은 같은 JobParameters로 다시 호출하면 실패한 스텝의 마지막 커밋 청크 뒤부터 이어 간다.

## 잡 1. dailySettlementJob

파라미터: `settlementDate`(KST 날짜, 기본 어제), `run.id`는 쓰지 않는다(같은 날짜 재실행이 재시작이 되게).

| 스텝 | 종류 | 읽기 | 처리 | 쓰기 | 청크 |
|---|---|---|---|---|---|
| clearDate | Tasklet | | 해당 날짜 daily_drop_settlement 삭제 | | |
| aggregateLedger | 청크 | `order_ledger WHERE occurred_at >= date 00:00 KST AND < 다음날`을 JdbcPagingItemReader로 id 순 | 드롭별 CONFIRMED와 CANCELED 수를 메모리 맵에 누적 | 스텝 끝에 맵을 daily_drop_settlement에 INSERT(Writer는 청크마다 호출되지만 실제 INSERT는 StepExecutionListener afterStep에서) | 1,000 |
| purgeOutbox | Tasklet | | `outbox WHERE status='PUBLISHED' AND published_at < now() - 7일` 삭제 | | |

aggregateLedger를 청크로 두는 이유는 100만 건 읽기를 페이지로 끊어 메모리를 상한 안에 두고, 실패 시 재시작 지점을 갖기 위해서다. 드롭이 10개뿐이라 집계 맵은 작다. 맵은 ExecutionContext에 저장해 재시작 때 복원한다.

재시작 실험: 50만 건째에 예외를 던지는 프로세서 플래그를 두고, 재실행하면 ExecutionContext의 마지막 읽기 위치와 맵에서 이어 간다. 결과 행의 수가 한 번에 돌린 것과 같아야 한다.

청크 크기 실험: 100, 1,000, 10,000으로 같은 100만 건을 돌려 처리 시간과 커밋 수를 표로 남긴다.

## 잡 2. reconciliationJob

파라미터: `dropId`(없으면 OPEN과 SOLD_OUT 드롭 전부), `run.at`(매 실행 고유).

| 스텝 | 종류 | 동작 |
|---|---|---|
| reconcile | Tasklet | 드롭마다 Redis `GET drop:{id}:stock`, `SCARD buyers`와 DB `COUNT(*) FILTER (WHERE status='CONFIRMED')`, `COUNT(*) FILTER (WHERE status='CANCELED')`를 읽어 diff = initial - redis_remaining - (confirmed - canceled). reconciliation_result INSERT. Redis 실패면 status REDIS_UNAVAILABLE, redis_remaining과 diff는 NULL |

DB 경로 플래그(ADR 0005)로 판 측정용 드롭은 Redis 재고 키가 없어 diff가 판매 수만큼 난다. 측정이 끝나면 그 드롭을 CLOSED로 바꿔 대조 범위(OPEN과 SOLD_OUT)에서 빠지게 한다.

diff가 0이 아니면 Prometheus 게이지 `dropgate_reconciliation_diff{drop}`에 값을 올리고 경보 하나가 잡는다. 자동 보정은 하지 않는다(결정, 보정은 사람이 본다).

## 호출과 스케줄

| 잡 | CronJob | 시각 |
|---|---|---|
| dailySettlementJob | settlement-daily | 매일 00:10 KST(15:10 UTC) |
| reconciliationJob | reconciliation-hourly | 매시 05분 |

CronJob 파드는 curl로 `POST /batch/jobs/daily-settlement`를 부른다. 배치 서비스는 항상 떠 있는 Deployment 1개다(JobLauncher 비동기, 상태는 GET으로). CronJob 자체를 Spring Batch 실행 파드로 만드는 방식(잡마다 JVM 기동)은 ADR 0013에서 비교만 하고 택하지 않는다. 이유는 재시작 상태 조회 API를 한곳에 두기 위해서다.

## 합성 데이터

load/seed-ledger.sql: 드롭 10개, 사용자 10만, order_ledger 100만 건(CONFIRMED 90만, CANCELED 10만), 2026-09-01에서 09-30 고르게. 인덱스 전후 EXPLAIN ANALYZE 대상 쿼리는 aggregateLedger의 범위 조회와 reconcile의 COUNT FILTER다.
