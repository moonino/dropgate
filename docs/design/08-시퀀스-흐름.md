# 08 시퀀스 흐름

## 1. 로그인

1. 브라우저 GET /auth/login/kakao -> 302 카카오 인가 페이지
2. 카카오 -> GET /auth/callback/kakao?code
3. auth-service가 code로 토큰을 받고 사용자 정보 조회(타임아웃 3초, 실패 시 502 KAKAO_UNAVAILABLE)
4. users UPSERT(kakao_id 기준), last_login_at 갱신
5. JWT RS256 액세스(15분, 클레임 sub, role, jti, iss dropgate-auth) + 리프레시(14일, Redis auth:refresh) 발급 -> 200

재발급: POST /auth/token/refresh. Redis에 리프레시 키가 있으면 삭제 뒤 새 쌍 발급(회전). 없으면 401. Redis 실패면 503 AUTH_UNAVAILABLE.

로그아웃: POST /auth/logout(Bearer). jti를 auth:revoked에 잔여 만료로 SET, 사용자의 리프레시 키 전부 DEL -> 204.

검증(모든 서비스): common 모듈 필터가 JWKS(10분 캐시)로 서명 확인 -> exp 확인 -> Redis `EXISTS auth:revoked:{jti}`(캐시 없음) -> 통과. Redis 실패 시 검증 실패로 처리하고 503 AUTH_UNAVAILABLE(ADR 0003, 무효화 확인을 건너뛰지 않는다).

## 2. 대기열 진입에서 구매까지

1. POST /api/drops/{id}/queue(Bearer). 드롭 meta status가 SCHEDULED나 CLOSED면 409 DROP_NOT_OPEN, SOLD_OUT이면 409 SOLD_OUT, buyers에 있으면 409 ALREADY_PURCHASED. `ZADD NX queue now userId` -> 202 {position, estimatedWaitSec}
2. 클라이언트가 GET /api/drops/{id}/queue/me를 2초마다 폴링. WAITING {position} 또는 ADMITTED {admittedUntil} 또는 NOT_IN_QUEUE. 대기 중 드롭이 OPEN이 아니게 되면 409(DROP_NOT_OPEN 또는 SOLD_OUT)를 받고 폴링을 끝낸다
3. 입장 스케줄러(1초마다, admit-lock 잡은 파드): ZPOPMIN rate명 -> 각자 admit 키 SET EX 60, admitted-count INCRBY
4. POST /api/drops/{id}/orders(Bearer). purchase.lua 실행
   - 성공: DB 트랜잭션(orders INSERT CONFIRMED, order_ledger INSERT, outbox INSERT) -> 201 {orderId}
   - DB 실패: compensate.lua(INCR stock, SREM buyers) -> 503 ORDER_PERSIST_FAILED
   - -1 DROP_NOT_OPEN 409, -2 NOT_ADMITTED 403, -3 ALREADY_PURCHASED 409, -4 SOLD_OUT 409
   - Redis 명령 실패나 200ms 초과: 503 STOCK_UNAVAILABLE, Retry-After 2
5. 재고가 0이 되면 Lua가 meta를 SOLD_OUT으로, 서비스가 drops.status를 SOLD_OUT으로 갱신(별 트랜잭션, 실패해도 Lua가 막으므로 무해)

1주 차 DB만 경로: 4번이 `UPDATE drops SET remaining_quantity = remaining_quantity - 1 WHERE id = ? AND remaining_quantity > 0 AND status = 'OPEN'` + orders INSERT(UNIQUE가 1인 1회) 한 트랜잭션. 영향 행 0이면 드롭 상태를 읽어 SCHEDULED나 CLOSED면 DROP_NOT_OPEN, OPEN이나 SOLD_OUT이면 SOLD_OUT. UNIQUE 위반은 롤백 뒤 ALREADY_PURCHASED. 차감이 UNIQUE보다 먼저라 이미 산 사용자가 품절 뒤 요청하면 SOLD_OUT을 받는다(Lua 순서와 다름, ADR 0005). 1주 차에는 대기열이 없으므로 입장 확인을 건너뛴다. 2주 차에 Redis 경로로 교체하고 DB 경로는 플래그로 남겨 기준선 재측정에 쓴다.

## 3. 주문 확정에서 알림까지

1. 릴레이(order 파드, 500ms): outbox PENDING 100건 FOR UPDATE SKIP LOCKED -> 건마다 XADD orders.events -> PUBLISHED, published_at
2. notification 소비자: XREADGROUP -> payload 파싱 -> DynamoDB PutItem(조건부) -> XACK
3. 이미 있으면(조건 실패) 성공으로 XACK. 예외면 ACK 안 함
4. 다른 파드가 30초 idle pending을 XCLAIM. 4회째는 DLQ

## 4. 취소와 보상

1. POST /api/orders/{id}/cancel(Bearer, 본인 주문만, 드롭 close_at 전만)
2. DB 트랜잭션: orders status CANCELED와 canceled_at(트리거 허용 전이), order_ledger INSERT CANCELED, outbox INSERT order.canceled
3. 커밋 뒤 cancel.lua(INCR stock, SREM buyers). SOLD_OUT이었으면 meta와 drops.status를 OPEN으로
4. 3이 실패하면 Prometheus 카운터 `dropgate_stock_compensation_failed_total{drop}`을 올리고 로그에 남긴다. outbox에 넣지 않는다(릴레이가 orders.events로 흘려보내 알림 소비자가 모르는 이벤트를 받게 된다). 대조 배치가 diff로 잡고 다음 대조 실행에서 사람이 본다(결정, 자동 재시도 없음)
5. 알림: order.canceled 이벤트가 3번 흐름을 탄다

순서 주의: DB 커밋 뒤 Redis 보상이라 그 사이 재고는 실제보다 1 적게 보인다. 반대 순서(Redis 먼저)면 Redis는 늘었는데 DB 취소가 실패해 초과 판매가 날 수 있다. 재고 과소가 과다보다 안전하다(ADR 0007).

## 5. 결산 배치

1. CronJob 15:10 UTC -> POST /batch/jobs/daily-settlement {settlementDate 어제}
2. JobLauncher 비동기 실행 -> 202 {executionId}
3. clearDate -> aggregateLedger(청크 1,000) -> purgeOutbox
4. CronJob은 완료를 기다리지 않는다. 상태는 GET /batch/jobs/{executionId}와 Prometheus 지표 `spring_batch_job_seconds`

실패 시: 다음 날 CronJob이 같은 날짜로 다시 호출하지 않으므로, 재시작은 수동(같은 settlementDate로 POST). 자동 재시작은 범위 밖.

## 6. 장애 시나리오별 동작

| 장애 | 동작 | 측정 |
|---|---|---|
| Redis 마스터 1대 다운 | Sentinel 절체 5에서 15초. 그동안 구매와 대기열 503. 절체 뒤 복구. 비동기 복제라 마지막 쓰기 유실 가능 -> 대조 diff | 절체 초, 503 수, diff |
| Redis 전체 다운 | 구매, 대기열, 로그인 재발급 503. 토큰 검증도 503(무효화 확인 불가). 드롭 조회와 내 주문 조회는 동작 | 503 수, 조회 성공률 |
| PostgreSQL 다운 | Lua 성공 뒤 DB 실패 -> compensate.lua로 Redis 되돌림 -> 503. 조회 전부 503 | 보상 성공률 |
| notification 파드 전부 다운 | Streams에 쌓임(MAXLEN 100만). 복구 뒤 pending부터 소비 | 회복 초, 건수 유지 |
| order 파드 1개 다운 | 나머지가 받음. 릴레이와 입장 스케줄러는 다른 파드가 락을 잡음 | 회복 초 |
| 카카오 다운 | 로그인만 502. 기존 토큰은 동작 | |
