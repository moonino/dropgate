# 08 시퀀스 흐름

## 1. 로그인

1. 브라우저 GET /auth/login/kakao -> 인가 요청(state 포함)을 서명된 HttpOnly 쿠키에 담고 302 카카오 인가 페이지. 서버 세션을 쓰지 않으므로 콜백이 다른 auth 파드로 가도 된다
2. 카카오 -> GET /auth/callback/kakao?code&state. 쿠키의 state와 비교해 다르면 400, 맞으면 쿠키를 지운다
3. auth-service가 code로 토큰을 받고 사용자 정보 조회(타임아웃 3초, 실패 시 502 KAKAO_UNAVAILABLE)
4. users UPSERT(kakao_id 기준), last_login_at 갱신
5. JWT RS256 액세스(15분, 클레임 sub, role, jti, iss dropgate-auth) + 리프레시(14일, Redis auth:refresh) 발급 -> 200. 리프레시는 store-refresh.lua(KEYS refresh 키, refresh-index. ARGV jti, TTL ms)로 refresh SET PX, index SADD, index PEXPIRE를 원자 처리한다. Redis에 쓰지 못하면 503 AUTH_UNAVAILABLE

웹 화면에서 로그인할 때는 web이 1번의 로그인 시작과 2번의 콜백을 auth-service로 중계하고, 5번의 토큰 쌍을 httpOnly 쿠키에 담는다. 그래서 카카오 Redirect URI는 web의 `/auth/callback/kakao`다(10 문서 4절, ADR 0020).

재발급: POST /auth/token/refresh. 리프레시 JWT의 서명, exp, iss, typ refresh를 검증한 뒤 새 쌍을 서명한다. rotate-refresh.lua(KEYS 옛 refresh 키, 새 refresh 키, refresh-index. ARGV 옛 jti, 새 jti, TTL ms)가 옛 키를 DEL한다. 결과가 0이면 아무것도 쓰지 않고 0을 반환해 401로 답하고 서명한 새 쌍은 버린다. 1이면 새 키 SET PX, index SREM 옛 jti와 SADD 새 jti, index PEXPIRE 뒤 1을 반환해 200으로 답한다. 같은 리프레시로 동시 재발급하면 하나만 200이다. Redis 실패면 503 AUTH_UNAVAILABLE.

로그아웃: POST /auth/logout(Bearer). logout.lua(KEYS revoked 키, refresh-index. ARGV 액세스 잔여 만료 ms, refresh 키 앞머리 `auth:refresh:{userId}:`)로 revoked SET PX, index의 jti마다 refresh 키 DEL, index DEL을 원자 처리한 뒤 204다. Redis 실패면 503 AUTH_UNAVAILABLE(02 문서 1절).

검증(모든 서비스): common 모듈 필터가 JWKS(10분 캐시, 조회 실패나 연결 3초나 읽기 3초 초과나 형식 오류면 503 AUTH_UNAVAILABLE, ADR 0018)로 서명 확인 -> exp 확인 -> Redis `EXISTS auth:revoked:{jti}`(캐시 없음) -> 통과. Redis 실패 시 검증 실패로 처리하고 503 AUTH_UNAVAILABLE(ADR 0003, 무효화 확인을 건너뛰지 않는다).

## 2. 대기열 진입에서 구매까지

1. POST /api/drops/{id}/queue(Bearer). 드롭 meta가 없거나 close_at이 지났으면 DROP_NOT_OPEN. DROP_NOT_OPEN 반환일 때만 DB에서 드롭 존재를 확인해 없으면 404 DROP_NOT_FOUND, 있으면 409 DROP_NOT_OPEN. status가 SOLD_OUT이면 409 SOLD_OUT, buyers에 있으면 409 ALREADY_PURCHASED. `ZADD NX queue now userId` -> 202 {position, estimatedWaitSec}
2. 클라이언트가 GET /api/drops/{id}/queue/me를 2초마다 폴링. WAITING {position} 또는 ADMITTED {admittedUntil} 또는 NOT_IN_QUEUE. 대기 중 드롭이 OPEN이 아니게 되면 409(DROP_NOT_OPEN 또는 SOLD_OUT)를 받고 폴링을 끝낸다
3. 입장 스케줄러(1초마다, admit-lock 잡은 파드): ZPOPMIN rate명 -> 각자 admit 키 SET EX 60, admitted-count INCRBY
4. POST /api/drops/{id}/orders(Bearer). purchase.lua 실행. meta 없음, status가 OPEN과 SOLD_OUT 중 하나가 아님, 서버 시각 ms가 meta close_at 이상이면 DROP_NOT_OPEN. SOLD_OUT도 입장, buyers, stock을 검사한다. 입장 확인이 꺼져 있거나 입장 검사를 통과했으면 기존 구매자는 ALREADY_PURCHASED, 신규 사용자는 SOLD_OUT. admit 키가 없고 입장 확인이 켜져 있으면 NOT_ADMITTED. DROP_NOT_OPEN 반환일 때만 DB에서 드롭 존재를 확인해 없으면 404 DROP_NOT_FOUND, 있으면 409 DROP_NOT_OPEN
   - 성공: DB 트랜잭션(orders INSERT CONFIRMED, order_ledger INSERT, outbox INSERT) -> 201 {orderId}
   - orders INSERT 0행(UNIQUE, 취소한 사용자의 재구매): compensate.lua 뒤 409 ALREADY_PURCHASED
   - DB 본문 쓰기를 flush하고 롤백 성공이 확인된 예외: compensate.lua 뒤 503 ORDER_PERSIST_FAILED. stock 또는 meta가 없으면 쓰기 없이 -1, 있으면 stock INCR과 buyers SREM, INCR 결과 1이고 meta SOLD_OUT이면 OPEN 복귀 후 복구 수량(1 이상) 반환
   - 커밋 결과 불확실(커밋 중이나 커밋 후 예외, 롤백 실패): 예약을 유지하고 자동 보상과 상태 동기화 없이 503 ORDER_PERSIST_FAILED, Retry-After 2. 실제 주문은 확정됐을 수 있다. `dropgate_order_commit_unknown_total{drop}`과 식별자를 담은 error 로그를 남기고 수동 복구한다(ADR 0021)
   - 보상 실패(-1 포함): `dropgate_stock_compensation_failed_total{drop}`과 error 로그를 남기고 원래 응답 코드를 유지하며 상태 동기화는 하지 않음. 대조가 불일치를 잡음
   - -1 DROP_NOT_OPEN 409, -2 NOT_ADMITTED 403, -3 ALREADY_PURCHASED 409, -4 SOLD_OUT 409
   - Redis 명령 실패나 200ms 초과: 503 STOCK_UNAVAILABLE, Retry-After 2
5. Lua는 남은 수량이 0이면 meta를 SOLD_OUT으로 바꾼다. 모든 성공 구매 확정과 성공 보상 뒤 synchronizeSaleStatus(dropId)를 새 DB 트랜잭션으로 호출한다. drops 행을 FOR UPDATE로 잠근 뒤 별도 문장의 새 READ COMMITTED 조회로 CONFIRMED 수를 읽어 DB 판매 상태를 맞춘다. CLOSED, SCHEDULED와 remaining_quantity는 유지하고 실패는 경고 로그만 남긴다(02 문서)

구매와 취소 구현은 purchase-path, 입장 확인은 queue.enabled 설정으로 고른다(02 문서 2절, ADR 0005). 2주 차는 입장 확인을 끄고 3주 차 대기열 PR에서 기본을 켠다. 전후 p99에 같은 스위치를 쓰고 꺼진 측정에는 대기열 비용이 없다고 적는다.

DB 경로(purchase-path=db): 4번이 `UPDATE drops SET remaining_quantity = remaining_quantity - 1 WHERE id = ? AND remaining_quantity > 0 AND status = 'OPEN'` + orders INSERT(UNIQUE가 1인 1회) 한 트랜잭션. 영향 행 0이면 드롭 상태를 읽어 SCHEDULED나 CLOSED면 DROP_NOT_OPEN, OPEN이나 SOLD_OUT이면 SOLD_OUT. UNIQUE 위반은 롤백 뒤 ALREADY_PURCHASED. 차감이 UNIQUE보다 먼저라 이미 산 사용자가 품절 뒤 요청하면 SOLD_OUT을 받는다(Lua 순서와 다름, ADR 0005). DB 경로는 기준선 재측정에 쓴다.

드롭 상태 스케줄러는 DB 전이 뒤 OPEN 드롭의 1회 초기화 권한을 별도 트랜잭션으로 커밋한 호출만 init.lua를 실행한다. 최초 실패나 Redis 키 유실 뒤에도 권한을 재사용하지 않는다. 키가 없으면 판매를 차단해 수동 복구하고 이미 성공한 키는 기존 계약대로 사용한다. DB 경로도 초기화 절차를 쓰지만 초기화 전 DROP_NOT_OPEN 규칙은 Redis 구매에 적용한다. 복구 전 모든 주문 인스턴스 중지, DB 트랜잭션 종료, 기존 Redis 클라이언트 연결과 미처리 쓰기 제거를 확인하고 복원 주문 수로 DB 판매 상태도 맞춘다. 계약과 복구 절차는 02 문서 2절을 따른다.

## 3. 주문 확정에서 알림까지

1. 릴레이(order 파드, 500ms): outbox PENDING 100건 FOR UPDATE SKIP LOCKED -> 건마다 XADD orders.events(MAXLEN 근사 트리밍 1,000,000) -> PUBLISHED, published_at. Redis 연결 실패나 타임아웃이면 attempts를 올리지 않고 남은 행을 건너뛰되 이미 발행한 행은 커밋한다. 그 밖의 실패만 10회째 FAILED와 카운터, error 로그(04 문서)
2. notification 소비자: XREADGROUP -> payload 파싱 -> DynamoDB PutItem(조건부) -> XACK
3. 이미 있으면(조건 실패) 성공으로 XACK. 예외면 ACK 안 함
4. 다른 파드가 30초 idle pending을 XCLAIM. 4회째는 DLQ

## 4. 취소와 보상

1. POST /api/orders/{id}/cancel(Bearer, 본인 주문만, 드롭 close_at 전만)
2. Redis 경로 DB 트랜잭션: orders status CANCELED와 canceled_at(트리거 허용 전이), order_ledger INSERT CANCELED, outbox INSERT order.canceled만 바꾼다
3. 커밋 뒤 cancel.lua(KEYS stock, buyers, meta. ARGV userId)는 stock 또는 meta가 없으면 쓰기 없이 -1을 반환한다. 있으면 stock INCR, buyers SREM 뒤 meta SOLD_OUT이면 OPEN으로 바꿔 1, 아니면 0을 반환한다. 0 또는 1인 성공일 때만 synchronizeSaleStatus(dropId)로 DB 판매 상태를 맞추고, 이 동기화 실패는 경고 로그만 남긴다
4. 3이 실패하거나 -1이면 취소 응답 200을 유지하고 Prometheus 카운터 `dropgate_stock_compensation_failed_total{drop}`을 올려 error 로그에 남긴다. outbox에 넣지 않는다(릴레이가 orders.events로 흘려보내 알림 소비자가 모르는 이벤트를 받게 된다). 대조 배치가 diff로 잡고 다음 대조 실행에서 사람이 본다(결정, 자동 재시도 없음)
5. 알림: order.canceled 이벤트가 3번 흐름을 탄다

DB 경로(purchase-path=db, ADR 0005, ADR 0019): 3번이 Redis가 아니라 2번 트랜잭션 안의 `UPDATE drops SET remaining_quantity = remaining_quantity + 1, status = CASE WHEN status = 'SOLD_OUT' THEN 'OPEN' ELSE status END WHERE id = ?`다. 재고와 주문이 같은 DB라 커밋 뒤로 미룰 이유가 없고, 4번 보상 실패도 없다. 검사 순서는 ORDER_NOT_FOUND(없는 주문), FORBIDDEN(남의 주문), ORDER_ALREADY_CANCELED, DROP_CLOSED(close_at이 지남)이고 주문 행을 FOR UPDATE로 잠근 뒤 검사한다. 검사를 통과하면 재고 복구 UPDATE를 주문 상태 UPDATE보다 먼저 한다. 구매는 drops 행을 잠근 채 orders에 INSERT하고, 이 INSERT의 (drop_id, user_id) 유일성 검사는 FOR UPDATE로 잠기기만 한 주문 행은 기다리지 않지만 끝나지 않은 트랜잭션이 UPDATE한 주문 행은 그 트랜잭션이 끝날 때까지 기다린다. 그래서 주문 상태 UPDATE를 먼저 하면 같은 사용자의 동시 재구매와 교착한다(취소는 drops 행을, 재구매는 취소가 바꾼 주문 행을 기다린다). 주문 행 잠금을 drops 행 잠금보다 먼저 잡아도 교착하지 않는 이유가 이것이다. 취소한 사용자는 UNIQUE 때문에 같은 드롭을 다시 살 수 없다(01 문서 결정).

순서 주의: DB 커밋 뒤 Redis 보상이라 그 사이 재고는 실제보다 1 적게 보인다. 반대 순서(Redis 먼저)면 Redis는 늘었는데 DB 취소가 실패해 초과 판매가 날 수 있다. 재고 과소가 과다보다 안전하다(ADR 0007).

## 5. 결산 배치

1. CronJob 15:10 UTC -> POST /batch/jobs/daily-settlement {settlementDate 어제}
2. JobLauncher 비동기 실행 -> 202 {executionId}
3. clearDate -> aggregateLedger(청크 1,000) -> purgeOutbox
4. CronJob은 완료를 기다리지 않는다. 상태는 GET /batch/jobs/{executionId}와 Prometheus 지표 `spring_batch_job_seconds`

실패 시: 다음 날 CronJob이 같은 날짜로 다시 호출하지 않으므로, 재시작은 수동(같은 settlementDate로 POST). 자동 재시작은 범위 밖.

## 6. 장애 시나리오별 동작

| 장애 | 동작 | 측정 |
|---|---|---|
| Redis 마스터 1대 다운 | Sentinel 절체 5에서 15초. 그동안 구매와 대기열 503. 절체 뒤 복구. 비동기 복제라 마지막 쓰기 유실 가능 -> 대조 diff | 절체 초, 503 수, diff |
| Redis 전체 다운 | 구매, 대기열, 로그인 재발급 503. 토큰 검증도 503(무효화 확인 불가)이라 내 주문 조회를 포함한 Bearer 엔드포인트 전부 503. 로그인 콜백도 503. 드롭 목록과 단건 조회는 remainingQuantity만 null로 200 유지. JWKS, 로그인 시작(302)도 동작. 재고 키 유실 복구는 판매 차단과 수동 복구(02 문서) | 503 수, 조회 성공률 |
| PostgreSQL 다운 | Lua 성공 뒤 롤백 확인이면 보상, 커밋 불확실이면 예약 유지와 수동 대조 -> 503. 조회 전부 503 | 보상 성공률, 커밋 불확실 건수 |
| notification 파드 전부 다운 | Streams에 쌓임(MAXLEN 100만). 복구 뒤 pending부터 소비 | 회복 초, 건수 유지 |
| order 파드 1개 다운 | 나머지가 받음. 릴레이와 입장 스케줄러는 다른 파드가 락을 잡음 | 회복 초 |
| 카카오 다운 | 로그인만 502. 기존 토큰은 동작 | |
