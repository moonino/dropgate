# 0008 outbox와 폴링 릴레이, Redis Streams

- 상태: accepted
- 날짜: 2026-10-19
- 관련: docs/design/01-ERD.md outbox, docs/design/02-Redis-키-설계.md 3절, docs/design/04-이벤트-명세.md 생산 규칙, docs/plan.md 2절 MSA 질문, 이슈 #110

## 맥락

주문 확정과 취소를 DB에 저장한 뒤 알림 서비스로 사건을 보내야 한다. DB 커밋과 이벤트 발행 사이에 파드가 죽어도 이벤트를 다시 찾을 수 있어야 하고, 재발행이 알림 중복으로 이어지지 않아야 한다.

## 결정

주문 트랜잭션에 outbox를 함께 쓰고 500ms 폴링 릴레이가 Redis Streams로 발행한다.

- 릴레이는 PENDING 100건을 FOR UPDATE SKIP LOCKED로 잡아 XADD 뒤 PUBLISHED로 바꾼다. XADD 성공 뒤 DB 갱신 전에 죽으면 재발행되므로 최소 1회 전달이고 소비자는 event_id(outbox id)로 멱등 처리한다.
- Redis 연결 실패와 타임아웃은 attempts에 세지 않고 그 틱의 남은 행을 건너뛴다. 이미 발행한 행은 커밋하고 나머지는 다음 틱에 다시 잡는다. 장애까지 10회에 세면 500ms 틱에서 절체 설계 구간 안에 정상 이벤트가 FAILED가 된다.
- 그 밖의 실패는 attempts를 올려 10회째 FAILED와 카운터, error 로그를 남긴다. occurred_at은 확정의 confirmedAt 또는 취소의 canceledAt으로 원장 시각과 같다.
- 여러 릴레이의 SKIP LOCKED 처리와 여러 소비자의 병렬 처리 때문에 같은 주문도 발행 순서와 소비 순서를 보장하지 않는다. 알림은 상태 병합이 아닌 사건 기록이므로 event_id별 멱등으로 저장한다.
- 이벤트 채널은 Redis가 이미 있으므로 Redis Streams로 둔다. XADD는 MAXLEN 근사 트리밍 1,000,000을 쓴다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| 커밋 뒤 직접 XADD | 릴레이가 없다 | 커밋과 발행 사이에 죽으면 이중 쓰기에서 이벤트가 유실된다 | 주문은 남고 알림을 복구할 근거가 없다 |
| CDC Debezium | DB 변경을 별도 릴레이 없이 읽는다 | 커넥터와 로그 운영이 스택에 더해진다 | 작은 비동기 경계 하나에 부담이 크다 |
| Kafka | 파티션, 보존과 재처리가 강하다 | 브로커와 운영 대상이 늘어난다 | Redis가 이미 있고 이 실험은 채널 하나로 충분하다 |

## 결과

건당 발행 지연은 정상 상태에서 폴링 대기 최대 500ms와 처리 시간이다. backlog와 장애가 있으면 더 길어진다. Streams의 근사 트리밍 기준은 100만 건이며 소비가 늦으면 소비 전 메시지가 잘릴 수 있다. 소비자 멱등과 재시작 복구는 4주 차에 검증하고 채널 교체는 8주 차 버퍼에서 다시 볼 수 있다.

측정으로 확인할 것: 합성 주문 1만 건에 알림이 정확히 1만 건이며 유실과 중복이 0인가? 소비자를 처리 중 종료했다 살려도 결과가 같고 pending이 0으로 돌아오기까지 몇 초인가?
