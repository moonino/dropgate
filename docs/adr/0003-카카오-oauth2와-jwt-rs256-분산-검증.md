# 0003 카카오 OAuth2와 JWT RS256 분산 검증

- 상태: accepted
- 날짜: 2026-10-04
- 관련: docs/design/02-Redis-키-설계.md 1절, docs/design/05-API-명세.md auth 엔드포인트, docs/design/08-시퀀스-흐름.md 1절, 이슈 #11

## 맥락

인증 인가 측정 질문은 "로그아웃한 토큰이 세 서비스 전부에서 거절되기까지 걸리는 시간이 100ms 안인가"다. 이 질문은 토큰 형식, 검증 위치, 무효화 방식이 정해져야 측정할 수 있다. 사용자는 카카오 계정만 쓰고, 결제가 없어 권한은 USER와 ADMIN 둘뿐이다.

## 결정

카카오 OAuth2로 로그인하고, auth 서비스가 RS256 JWT 액세스 토큰(15분)과 리프레시 토큰(14일, Redis, 회전)을 발급하며, 각 서비스는 JWKS(10분 캐시)로 서명을 스스로 검증한 뒤 요청마다 Redis 무효화 목록을 확인한다.

- RS256을 쓰는 이유는 검증하는 쪽(order, notification)이 개인키를 가질 필요가 없어서다. batch는 클러스터 안에서만 호출되고 Bearer를 받지 않으므로 검증 주체가 아니다. 공개키만 JWKS로 받으면 되므로 서비스가 늘어도 비밀이 늘지 않는다.
- 각 서비스가 직접 검증하는 이유는 서비스 사이 동기 호출을 두지 않는다는 경계 규칙(ADR 0002) 때문이다. 게이트웨이에서 한 번만 검증하면 측정 질문의 "세 서비스 전부에서"가 사라진다.
- 무효화 목록을 요청마다 Redis EXISTS로 확인하고 캐시하지 않는 이유는 100ms 목표가 그래야 성립해서다. 캐시를 두면 거절 시간이 캐시 TTL이 되고 측정할 것이 없어진다.
- Redis를 못 읽으면 검증을 건너뛰지 않고 503 AUTH_UNAVAILABLE을 돌려준다. 무효화된 토큰을 통과시키는 것보다 잠시 거절하는 쪽이 안전하다. Redis 전체 장애 정책(ADR 0006)과 같은 방향이다.
- 리프레시는 회전한다. 재발급 때 옛 리프레시 키를 지우고 새 키를 만든다. 탈취된 리프레시가 한 번 쓰이면 원래 사용자의 다음 재발급이 실패해 드러난다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| 서버 세션(Redis 세션 저장소) | 로그아웃이 즉시고 단순하다 | 모든 서비스가 요청마다 세션 전체를 읽는다. JWT 검증과 JWKS 분산이라는 실험 대상이 사라진다 | 측정 질문이 JWT 전제다 |
| HS256 공유 비밀 | 라이브러리가 단순하고 빠르다 | 검증하는 모든 서비스가 서명 비밀을 가진다. 하나가 새면 전부 위조 가능 | 비밀을 auth 하나에만 두고 싶다 |
| 무효화 없이 짧은 만료만(5분) | Redis 의존이 없다 | 로그아웃 뒤 최대 5분 유효. 측정 질문 자체가 성립하지 않는다 | 로그아웃 즉시 무효화가 실험 대상이다 |
| API 게이트웨이에서 한 번만 검증 | 서비스 코드가 단순하다 | 게이트웨이 뒤에서는 서비스가 서로를 믿어야 한다. "세 서비스 전부에서" 측정이 불가능하다 | 분산 검증이 실험 대상이다 |

## 결과

- Bearer 엔드포인트 전부가 요청마다 Redis 왕복 1회를 더 한다. 이 비용은 기준선 측정(ADR 0005)의 p99에 포함돼 기록된다.
- Redis 전체 장애 때 드롭 목록과 단건 조회, JWKS처럼 인증이 없는 공개 엔드포인트만 살아 있고, 내 주문 조회를 포함해 Bearer가 붙은 엔드포인트는 전부 503이다.
- 서명 키는 kid 하나이고 회전은 범위 밖이다. K8s Secret의 PEM을 바꾸면 기존 토큰이 전부 무효가 된다. 7주 안에는 회전하지 않는다.
- 관리자 승격은 시드로만 한다. 승격 API가 없으므로 권한 상승 경로가 없다.
- 측정으로 확인할 것: 로그아웃 직후 세 서비스에 같은 액세스 토큰으로 요청했을 때 401이 되기까지 몇 ms인가. 목표 100ms.
