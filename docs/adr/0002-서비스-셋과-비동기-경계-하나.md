# 0002 서비스 셋과 비동기 경계 하나

- 상태: accepted
- 날짜: 2026-10-04
- 관련: docs/design/00-설계-개요.md 3절, docs/design/01-ERD.md 스키마 분리, docs/plan.md 1절과 6절, 이슈 #11

## 맥락

MSA 측정 질문은 셋이다. 주문 1만 건에 알림이 정확히 1만 건인가, 소비자를 죽였다 살려도 결과가 같은가, 취소 시 재고가 정확히 복구되는가. 앞의 둘과 인증 질문(로그아웃 토큰이 세 서비스에서 거절되는 시간)에 답하려면 서비스 사이에 실제 경계가 있어야 한다. 셋째는 주문 서비스 안(Redis 재고 복구와 DB)에서 끝난다. 반대로 경계가 많아지면 7주 안에 못 끝내고, 측정 질문과 상관없는 운영 부담만 는다. 얼마나 나눌지 코드 전에 정해야 모듈 구조와 DB 권한이 따라온다.

## 결정

서비스 셋(auth, order, notification)과 배치(settlement) 하나로 나누고, 비동기 경계는 주문에서 알림으로 가는 Redis Streams 하나만 둔다.

- 나누는 기준은 측정 질문이다. 알림을 떼어내야 outbox, 멱등 소비, 소비자 재시작 실험이 성립한다. 인증을 떼어내야 JWKS 분산 검증과 로그아웃 전파 시간(100ms 목표) 실험이 성립한다. 배치를 떼어내야 CronJob과 재시작 실험이 성립한다.
- 더 나누지 않는 이유는 그 이상의 경계가 어떤 측정 질문에도 답하지 않기 때문이다. 드롭, 대기열, 주문을 한 서비스에 두는 이유는 구매 Lua가 재고, 입장 키, 구매자 집합을 한 드롭 아래 키로 원자 처리해야 해서다.
- 경계 규칙 셋. 서비스는 다른 서비스의 스키마를 읽지 않는다(PostgreSQL 인스턴스 하나, 스키마 셋, 서비스별 DB 사용자로 권한에서 막는다). 서비스 사이 동기 호출은 없다(사용자 식별은 JWT의 sub로 끝낸다). 알림에 필요한 값은 이벤트에 싣는다(dropName).
- 예외 하나. 결산 배치는 주문 서비스의 데이터(orders 스키마 읽기 전용, 대조용 Redis 재고와 구매자 키 읽기)를 직접 본다. 배치는 주문 서비스의 소유로 보고, 결산이 이벤트를 다시 집계하는 것보다 원장 테이블을 직접 읽는 것이 단순하고 정확하다. Redis 읽기는 DB 권한처럼 막지 못하므로 코드 리뷰로 지킨다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| 모놀리스 하나 | 가장 단순. 트랜잭션 하나로 끝난다 | outbox, 멱등 소비, JWKS 분산 검증 실험이 성립하지 않는다 | MSA 질문 둘(알림 정확도, 소비자 재시작)과 인증 질문(로그아웃 전파)을 못 답한다 |
| 드롭, 대기열, 주문을 각각 서비스로 | 경계가 많아 MSA 같아 보인다 | 구매 원자성이 서비스 경계를 넘어가 Saga가 필요해진다. 측정 질문에 없는 복잡도 | 재고 정확도 측정이 오히려 흐려진다 |
| 동기 REST 호출 허용 | 알림 서비스가 드롭 이름을 조회하면 이벤트가 작아진다 | 주문 서비스 장애가 알림으로 전파되고, 비동기 경계 실험(소비자 종료 뒤 회복)이 섞인다 | 경계 하나를 깨끗하게 유지하는 것이 측정에 중요하다 |

## 결과

- 이벤트 payload에 dropName이 중복 저장된다. 드롭 이름을 바꾸면 과거 알림에는 반영되지 않는다(알림은 사건 기록이라 수용).
- orders.user_id는 users.id를 가리키지만 FK가 없다. 정합성은 JWT 발급 쪽이 책임진다.
- 축소 순서(플랜 6절) 1번이 "인증 서비스를 주문 서비스에 합침"이다. 그 경우 JWKS 분산 검증 실험은 두 서비스(order, notification) 사이에서만 남는다.
- 다시 볼 조건: 4주 차 알림 실험에서 유실이나 중복이 0이 아니고 outbox와 멱등 소비(0008, 0012)를 고쳐도 남으면, 이 분리 자체를 다시 본다.
