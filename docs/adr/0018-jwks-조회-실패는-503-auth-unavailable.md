# 0018 JWKS 조회 실패는 503 AUTH_UNAVAILABLE

- 상태: accepted
- 날짜: 2026-10-17
- 관련: docs/design/05-API-명세.md 오류 코드표 AUTH_UNAVAILABLE, docs/design/08-시퀀스-흐름.md 1절 검증, ADR 0003, 이슈 #6

## 맥락

ADR 0003과 08 문서는 각 서비스가 JWKS(10분 캐시)로 서명을 검증한다고 정했지만, 캐시가 비었거나 만료된 순간 auth의 JWKS를 받지 못하면 어떤 응답을 낼지는 정하지 않았다. 오류 코드표의 AUTH_UNAVAILABLE 뜻은 Redis 실패만 적었다. common 모듈 필터(이슈 #6)를 만들면서 이 경우의 코드와 대기 상한을 정해야 했다.

## 결정

JWKS를 받지 못하거나, 3초 안에 연결되지 않거나 읽는 중 3초 동안 응답이 없거나, 본문이 JWKS 형식이 아니면 토큰 검증을 실패로 보고 503 AUTH_UNAVAILABLE과 Retry-After 2로 답한다.

- 401로 답하면 클라이언트는 토큰이 나쁘다고 보고 다시 로그인한다. 원인은 토큰이 아니라 auth 쪽 장애이므로 Redis 무효화 확인 실패와 같은 503으로 묶는다.
- 연결 3초와 읽기 3초는 외부 호출 상한으로 이미 쓰는 카카오 호출(연결 3초, 읽기 3초)과 맞춘 값이다. 측정 근거는 아직 없다(추정). 갱신은 파드마다 10분에 한 번이라 대부분의 요청은 이 대기를 겪지 않는다.
- 캐시 만료를 함께 본 요청들은 진행 중인 조회 하나를 기다려 그 결과(키 또는 503)를 같이 받는다. 기다리던 요청이 저마다 다시 조회하면 대기가 요청 수만큼 쌓여 상한이 깨진다. 실패는 따로 기억하지 않으므로 실패 뒤에 새로 온 요청은 다시 조회한다.
- 만료된 캐시를 실패 때 계속 쓰지 않는다. 서명 키 회전은 범위 밖이고(01 문서, kid 하나) 갱신 실패를 숨기면 auth 장애를 늦게 알게 된다.
- JWKS에 없는 kid는 다시 받지 않고 401로 거부한다. kid가 하나뿐이라 모르는 kid는 위조나 다른 발급자의 토큰이다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| 401 UNAUTHENTICATED | 코드가 하나 줄어든다 | 장애 때 정상 사용자가 전부 로그아웃된다 | 원인이 토큰이 아니다 |
| 만료 캐시를 실패 때 계속 사용 | auth 장애 중에도 검증이 된다 | 장애가 가려지고 캐시 수명이 사실상 무한이 된다 | 키 회전이 없어 얻는 것이 적다 |
| 모르는 kid면 즉시 다시 받기 | 키 회전에 바로 따라간다 | 위조 토큰마다 auth로 요청이 간다 | 키 회전이 범위 밖이다 |

## 결과

auth가 내려가 있는 동안 캐시가 만료된 파드는 Bearer 요청에 503을 낸다. 7주 차 장애 주입에서 확인할 것: auth 파드를 모두 내렸을 때 order의 Bearer 요청이 캐시 만료 전까지 200, 만료 뒤 503으로 바뀌는가. 3초 제한이 p99에 주는 영향은 측정 뒤 다시 본다.

한 번 조회의 전체 시간에는 상한이 없다. 보통 연결과 읽기를 합쳐 약 6초까지 걸리고, 본문을 조금씩 흘려보내는 서버면 그보다 길어질 수 있다(코드 추론, 측정 아님). 조회를 기다리는 동안 Bearer 요청 스레드가 묶이므로 공개 경로가 느려지는지도 7주 차 장애 주입에서 함께 본다. 형식은 맞지만 키가 없거나 다른 키가 든 JWKS를 받으면 503이 아니라 모든 토큰이 401이 되고 그 결과가 10분 캐시된다. auth 설정 실수가 전원 로그아웃으로 이어질 수 있는 경계 사례로 남겨 같은 때 다시 본다.
