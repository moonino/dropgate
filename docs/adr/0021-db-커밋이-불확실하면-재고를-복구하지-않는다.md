# 0021 DB 커밋이 불확실하면 재고를 복구하지 않는다

- 상태: accepted
- 날짜: 2026-10-19
- 관련: ADR 0007, docs/design/02-Redis-키-설계.md 2절, docs/design/08-시퀀스-흐름.md 2절과 6절, 이슈 #113

## 맥락

ADR 0007은 Lua 성공 뒤 DB 예외가 나면 재고를 보상한다. 그러나 DB가 COMMIT을 끝내고 응답만 유실하거나 커밋 후 콜백이 실패하면 호출자는 예외를 받아도 CONFIRMED 주문은 남는다. 이때 Redis 재고를 늘리면 다른 사용자의 구매를 허용해 초과 판매할 수 있다. 롤백 자체의 실패도 주문이 없다는 근거가 되지 않는다.

## 결정

DB 롤백이 확인된 구매 실패만 Redis 보상을 하고, 커밋 결과가 불확실하면 예약을 유지한다. ADR 0007의 Lua 판정, 초기화 권한, 자동 재전송 금지, 판매 상태 동기화와 취소 순서는 그대로 채택한다.

- 주문 저장 트랜잭션 본문에서 orders, order_ledger, outbox 쓰기를 flush까지 끝낸다. INSERT 0행과 본문 실패는 전용 예외로 전파한다.
- 트랜잭션 경계가 롤백을 성공적으로 마치고 전용 예외를 그대로 돌려준 경우에만 compensate.lua를 호출한다. INSERT 0행은 409 ALREADY_PURCHASED, 그 밖의 본문 실패는 503 ORDER_PERSIST_FAILED다. 보상 실패 처리도 기존 규칙을 유지한다.
- 커밋 중 예외, 커밋 후 예외와 롤백 실패로 감싸진 예외는 결과 불확실이다. 원인 체인에서 전용 예외를 찾아 롤백 성공으로 간주하지 않는다. 재고와 buyers를 유지하고 Lua 재실행이나 자동 보상을 하지 않으며 503 ORDER_PERSIST_FAILED와 Retry-After 2를 반환한다.
- 결과 불확실은 `dropgate_order_commit_unknown_total{drop}`과 드롭, 사용자, 확인 가능한 주문 식별자를 담은 error 로그로 남긴다. DB 판매 상태 동기화도 자동 실행하지 않는다.
- 사용자는 503 뒤에도 내 주문 조회에서 확정 주문을 확인할 수 있다. 운영자는 모든 주문 인스턴스를 멈추고 진행 중 DB 트랜잭션과 Redis 쓰기를 제거한 뒤 실제 CONFIRMED 주문으로 재고, buyers, DB 판매 상태를 수동 복원한다. 02 문서의 기존 복구 절차를 따른다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| 모든 DB 예외를 즉시 보상 | 실패한 예약이 빨리 풀린다 | 실제 커밋된 주문의 재고를 다시 팔 수 있다 | 초과 판매를 막지 못한다 |
| 예외 뒤 주문 유무를 한 번 조회해 판정 | 일부 결과를 자동 확인한다 | 기존 트랜잭션 종료와 조회 순서를 확정하지 못하면 없는 주문으로 오판한다 | 현재는 수동 대조 경계를 유지한다 |
| 모든 DB 실패에서 예약 유지 | 예외 분류가 단순하다 | 확인된 롤백에도 재고가 묶인다 | 안전하게 확인한 롤백은 기존 보상이 가능하다 |

## 결과

커밋 불확실 때 재고가 실제보다 적게 남을 수 있다. 가용성을 낮추고 수동 복구 비용을 내는 대신 재고 과다를 막는다. 실제 PostgreSQL 커밋 후 콜백에서 예외를 내는 테스트로 CONFIRMED 주문이 남아도 추가 구매가 차단됨을 검증한다. 롤백 실패로 전용 예외가 감싸진 경우에도 자동 보상이 없는지 별도로 고정한다.
