# 0006 Redis 전체 장애 정책은 막기

- 상태: accepted
- 날짜: 2026-10-19
- 관련: docs/design/02-Redis-키-설계.md 2절, docs/design/08-시퀀스-흐름.md 6절, docs/plan.md 2절 Redis 전체 장애 질문, 이슈 #110

## 맥락

2주 차부터 재고의 정본은 Redis이고 DB의 remaining_quantity는 기준선 측정용이다(ADR 0005). Redis를 읽지 못할 때 판매와 토큰 검증을 계속할지 정해야 장애 테스트의 기대 응답이 고정된다.

## 결정

Redis 전체 장애 때 판매와 토큰 검증을 막고, 공개 조회는 남은 수량 없이 연다.

- 재고와 대기열 명령 실패나 200ms 초과는 503 STOCK_UNAVAILABLE, 무효화 확인과 리프레시 명령 실패는 503 AUTH_UNAVAILABLE이다. Retry-After는 2초다.
- Bearer 엔드포인트는 내 주문 조회까지 전부 503이다. 로그인 콜백과 재발급도 리프레시 저장 때문에 503이다. 드롭 목록과 단건은 remainingQuantity만 null로 HTTP 200을 유지하고, JWKS와 로그인 시작은 계속 동작한다.
- 초기화 권한은 drops.stock_initialization_claimed에 1회 영속 저장하고 별도 DB 트랜잭션으로 커밋한 호출만 init.lua를 실행한다. 처음 실패해도 권한을 유지하고 자동 재시도하지 않는다. meta 유실 뒤 total_quantity로 다시 만들면 기존 주문만큼 초과 판매할 수 있어 판매 차단과 수동 복구를 택한다.
- DB 경로로 자동 전환하지 않는다. Redis와 DB가 각각 판매를 허용하면 복구 때 재고를 합칠 기준이 둘이 된다. 무효화 조회 실패 때 검증을 생략하지 않는 ADR 0003과 같은 방향이다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| DB 경로 폴백 | 장애 중에도 판매한다 | 재고 정본이 둘이 되어 복구 때 초과 판매 위험이 생긴다 | 8주 차 버퍼에서 막기 정책과 수치로 비교한다 |
| 요청을 큐에 담아 나중 처리 | 요청을 보관한다 | 즉시 확정 대신 접수라는 응답 의미와 조회 흐름이 필요하다 | 측정 범위가 커진다 |

## 결과

Redis 장애가 서비스 전체 종료로 번지지 않게 order의 readiness는 유지하고 Redis 상태는 별 지표로 본다(07 문서). 데이터가 유지된 연결 장애 복구는 같은 경로로 재개한다. 키 유실이나 최초 초기화 실패는 모든 주문 인스턴스 중지와 진행 중 DB 트랜잭션 종료를 확인한 뒤 CONFIRMED 주문으로 stock, buyers, meta와 TTL을 수동 복원하고 재개한다. 자동 재시도의 가용성을 포기해 진행 중 주문을 놓치는 재초기화를 막는다.

측정으로 확인할 것: Redis 전부 종료 중 합성 구매 요청이 정책대로 거절되고 초과 판매가 0인가? remainingQuantity가 null인 드롭 조회는 200을 유지하는가? 거절 수와 조회 성공률은 얼마인가?
