# 0007 재고 차감은 Lua 한 스크립트

- 상태: accepted
- 날짜: 2026-10-19
- 관련: docs/design/02-Redis-키-설계.md 2절, docs/design/08-시퀀스-흐름.md 2절과 4절, docs/plan.md 2절 Redis 정확도 질문, 이슈 #110

## 맥락

동시 구매에서 열림, 입장, 1인 1회, 재고를 따로 읽고 쓰면 검사와 차감 사이에 다른 요청이 끼어든다. Redis와 주문 DB는 한 트랜잭션으로 묶을 수 없으므로 차감 뒤 DB 실패와 취소의 복구 순서도 정해야 한다.

## 결정

구매 판정과 차감을 purchase.lua 한 스크립트로 원자 처리하고 분산 락을 쓰지 않는다.

- meta status가 OPEN 또는 SOLD_OUT인지와 close_at, 설정에 따른 입장 키, buyers, stock을 순서대로 검사하고 차감과 buyers 추가를 함께 한다. 입장 확인이 꺼져 있거나 입장 검사를 통과했으면 SOLD_OUT에서도 buyers를 stock보다 먼저 검사하므로 기존 구매자는 ALREADY_PURCHASED, 신규 사용자는 SOLD_OUT이다. 입장 확인이 켜져 있고 admit 키가 없으면 NOT_ADMITTED다. 판정에 필요한 키가 한 드롭 아래에 있다.
- Lua 성공 뒤 orders, order_ledger, outbox를 한 DB 트랜잭션에 쓴다. UNIQUE로 INSERT 0행이면 보상 뒤 ALREADY_PURCHASED, DB 예외면 보상 뒤 ORDER_PERSIST_FAILED다.
- compensate.lua는 stock INCR, buyers SREM과 마지막 재고 실패의 SOLD_OUT 복귀를 함께 하고 복구 수량(1 이상)을 반환한다. compensate.lua와 cancel.lua는 stock 또는 meta가 없으면 아무 쓰기도 하지 않고 -1을 반환한다. 래퍼는 -1을 보상 실패로 다뤄 원래 응답 코드와 카운터, error 로그 규칙을 유지하며 상태 동기화는 하지 않는다. 키를 재생성하지 않고 수동 복원에서 Redis와 DB 판매 상태를 같은 CONFIRMED 수에 맞춘다.
- 초기화 권한은 DB의 1회 claim을 먼저 커밋해 얻는다. 실행 여부를 모르는 초기화 실패나 Redis 키 유실 뒤에는 자동 재시도하지 않는다. 키가 없을 때는 이미 팔린 수량을 무시한 재초기화를 막기 위해 가용성보다 수동 복구를 택하고 이미 성공한 키는 기존 계약대로 사용한다(ADR 0006).
- Lettuce의 재연결은 유지하지만 자동 명령 replay와 앱의 Lua 재시도는 막는다(02 문서 공통 클라이언트 경계). 기본 재전송은 DB의 1회 권한 밖에서 init를 다시 실행하거나 INCR 보상을 중복시킬 수 있다. 응답 유실은 실행 실패를 뜻하지 않으므로 대조와 수동 복구로 남긴다.
- 모든 성공 구매 확정, 성공 보상, 성공 취소 뒤 synchronizeSaleStatus(dropId)를 새 DB 트랜잭션으로 호출한다. drops 행 FOR UPDATE 뒤 별도 문장의 새 READ COMMITTED 조회로 CONFIRMED 수를 읽어 total_quantity와 같으면 SOLD_OUT, 작으면 OPEN으로 맞춘다. CLOSED, SCHEDULED와 remaining_quantity는 유지하고 실패는 경고로 남긴다. 마지막 구매만 동기화하면 앞선 예약의 지연 확정 뒤 OPEN이 남고, 단순 상태 UPDATE는 늦은 구매와 취소 또는 보상 순서에 따라 SOLD_OUT이 남는다.
- 취소는 DB 커밋 뒤 cancel.lua로 재고를 돌린다. Redis부터 늘리면 DB 취소 실패 중 초과 판매가 가능하다. 커밋 뒤 보상 사이에 재고가 실제보다 적게 보이는 쪽을 택한다. 취소 보상 실패도 자동 재시도 없이 대조로 잡는다.

## 대안

| 대안 | 장점 | 단점 | 안 고른 이유 |
|---|---|---|---|
| Redisson 분산 락 뒤 DB 차감 | 임계 구역이 명시적이다 | 락 왕복이 늘고 보유 파드가 죽으면 만료까지 막힌다 | Redis 한 스크립트로 필요한 판정을 묶을 수 있다 |
| WATCH와 MULTI | 낙관적으로 갱신한다 | 같은 재고 경합에서 재시도가 늘어난다 | 재시도 전략이 정확도와 p99 측정에 섞인다 |
| DB 행 잠금 | 재고와 주문을 한 트랜잭션으로 묶는다 | 같은 drops 행에서 요청이 줄을 선다 | ADR 0005의 기준선으로 남겨 비교한다 |

## 결과

재고 판정 로직이 Lua에 있으므로 Testcontainers의 실제 Redis로 반환 순서, 동시 차감, 보상과 만료를 검증한다. Redis와 DB 사이 실패 창은 남고 대조가 이를 드러낸다. 구매와 취소는 purchase-path 설정으로 함께 선택한다. 성공 경로는 DB 행 잠금으로 상태를 동기화하는 비용을 내고 Redis 거절 경로는 이 잠금을 피한다. 수량뿐 아니라 최종 DB 판매 상태도 실제 PostgreSQL과 Redis의 순서 제어 테스트로 고정한다.

측정으로 확인할 것: 재고 100개에 합성 구매 요청 1만 건을 파드 3개로 보내면 성공이 정확히 100건이며 초과와 중복이 0인가? 같은 명령의 DB 기준선과 p99는 얼마나 다른가? 취소 1,000건 뒤 대조 차가 0인가?
