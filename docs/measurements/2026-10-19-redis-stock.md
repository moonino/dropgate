## 환경

## 스크립트 단계

1. 구매 경로 db 또는 redis를 선택하고 JDK 21을 확인한 뒤 order-service bootJar를 빌드한다. 실행 대상은 plain JAR를 제외한 단일 JAR다.
2. 실행마다 측정용 RSA 키와 정적 JWKS, ADMIN 토큰 및 구매 토큰을 만든다. 사용자 8000명 중 1000명이 같은 토큰으로 3회, 나머지 7000명이 1회 요청해 총 10000건을 구성한다. 추가 재요청은 2000건이다.
3. 새 PostgreSQL과 Redis 및 JWKS 컨테이너를 시작한다. PostgreSQL 준비 후 orders 스키마와 order_user를 만들고 Redis PING과 JWKS 응답을 확인한다. DB와 Redis의 데이터는 이전 실행에서 이어받지 않는다.
4. order-service JVM 1개를 선택한 구매 경로와 대기열 꺼짐 설정으로 시작한다. DB, Redis와 JWKS 주소를 주입하고 Bearer 인증을 거친 health 응답과 서비스 PID의 생존을 기다린다.
5. ADMIN 요청으로 재고 100개인 드롭을 생성한다. 스케줄러가 OPEN으로 전이하고 Redis stock이 100이 될 때까지 기다린다. 두 구매 경로 모두 이 준비 절차를 거친다.
6. 서비스 생존을 확인하고 k6 shared-iterations로 VU 500, 총 10000건, 최대 5분의 구매 부하를 보낸다. 응답은 201, 409 SOLD_OUT과 409 ALREADY_PURCHASED로 분류하고 다른 응답은 purchase_unexpected에 기록한다. k6는 그 카운터가 0이어야 통과한다. 같은 토큰의 재요청이 같은 VU에서 순서대로 실행된다고 가정하지 않는다.
7. 부하 후 서비스 생존과 outbox PENDING 배출을 확인한다. reconcile.sh로 주문, 재고와 outbox를 모드에 맞게 대조하고 요청 및 확정 건수와 발행 완료 조건을 확인한다. 요약, 환경과 SHA-256을 기록한 뒤 임시 파일을 mv해 완료 manifest를 남긴다. EXIT 정리에서는 해당 실행의 서비스와 컨테이너를 종료한다. 실패한 실행은 정상 완료 기록에 섞지 않는다.

## 같은 날 DB와 Redis의 수치 차이

아래 차이는 Redis 중앙값 빼기 DB 중앙값이며 변화율은 그 차이를 DB 중앙값으로 나눈 백분율이다. 응답 시간과 요청/초를 같은 방향의 개선으로 해석하지 않는다.

| 최대(ms) | 751.30 | 2185.26 | 1433.96 | 190.86 |
| 요청/초 | 2427.55 | 4296.55 | 1869.00 | 76.99 |

## 해석

각 실행의 성공은 100건이고 중복, 초과 판매와 모드별 검사 차는 모두 0이다. outbox는 PENDING 0, FAILED 0, PUBLISHED 100이며 XLEN도 100이다. 이 측정은 발행까지 확인하며 알림 소비 완료를 뜻하지 않는다.

전체 p99 중앙값은 DB 640.55ms, Redis 216.23ms로 DB 대비 66.24% 낮았다. 전체 요청/초 중앙값은 2427.55에서 4296.55로 DB 대비 76.99% 높았다. 그러나 201 p99 중앙값은 DB 545.54ms에서 Redis 2182.81ms로 300.12% 늘었다. 전체 최대 지연 중앙값도 Redis가 높다. 요청의 99%가 409인 구성이라 전체 지표만으로 성공 구매가 빨라졌다고 해석할 수 없다. 성공 요청의 내부 병목 원인은 이번에 프로파일링하지 않았다.

DB의 ALREADY_PURCHASED는 15에서 22건, Redis는 30에서 46건이다. [API 순서](../design/05-API-명세.md)와 [ADR0005](../adr/0005-db만으로-먼저-만들고-redis는-나중에.md)대로 DB는 차감 뒤 UNIQUE를 확인하므로 품절 후 SOLD_OUT이 먼저 나올 수 있다. 대기열을 끈 Redis는 buyers를 stock보다 먼저 확인한다. 응답 분포 차이를 정확도 오류로 판정하지 않는다.

## 10월 17일 기준선과의 차이

[10월 17일 기준선](2026-10-17-db-only-baseline.md)은 DB 7회이며 표의 정수 표시값으로 계산했다. 당시 재현 명령은 ./load/db-only-baseline.sh다. 아래는 실행별 전체 지표의 중앙값과 범위이며 표본을 합친 백분위수가 아니다.

| 지표 | 10월 17일 DB 7회 | 이번 DB 5회 | 이번 Redis 5회 |
|---|---|---|---|
| 전체 p99(ms) | 861 (652에서 1164) | 640.55 (597.88에서 666.56) | 216.23 (171.39에서 230.02) |
| 요청/초 | 1839 (1733에서 2649) | 2427.55 (2212.45에서 2476.44) | 4296.55 (4102.25에서 4555.64) |

과거 DB 중앙값 대비 이번 DB는 p99 -220.45ms, 요청/초 588.55이며, Redis는 p99 -644.77ms, 요청/초 2457.55다. 과거 중앙값은 원문 7행으로 다음처럼 구한다.

```sh
python3 -c 'from statistics import median; print(median([817,652,698,1164,971,861,905]), median([2281,2649,2631,1756,1839,1733,1793]))'
```

과거 기준선에는 Redis가 없었다. 이번 DB도 Redis OPEN 초기화, Bearer 무효화 조회와 outbox 릴레이가 있다. 호스트와 주요 버전 표기가 같아도 소스와 실행 내용, 횟수와 동시 작업이 달라 차이 전부를 재고 Lua의 인과 효과로 단정하지 않는다.

## 비교할 때 지킬 것

- 대기열 꺼짐, 단일 Redis, 서비스 JVM 1개다. 파드 3개, Sentinel 절체, 대기열 켜짐과 알림 소비 및 결산 부하는 포함하지 않는다.
- k6와 JVM, DB 및 Redis가 같은 Mac의 자원을 공유한다. 다른 사용자 앱과 컨테이너를 중단하거나 자원을 격리하지 않았다. 로컬 서비스 테스트와 Next.js 빌드는 함께 실행하지 않았다.
- `uptime`의 1분 load average는 시작 전 2.74, 완료 후 9.53이었다. 두 시점만 관측했으며 실행 중 피크나 개별 프로세스의 CPU는 측정하지 않았다.
- 매번 새 JVM, DB와 Redis를 썼고 별도 부하 예열은 없다. 다만 health, 드롭 생성과 초기화 준비 요청은 부하 전에 있다.
- 고정 교대 순서이며 무작위 실험이 아니다. 각 실행과 중앙값 및 범위를 함께 보고 최고값만 선택하지 않는다.
- HTTP 지연과 요청/초에는 준비 및 outbox 배출 대기 전체 시간이 포함되지 않는다. 응답별 max>=0은 지표를 내보내는 조건이며 지연 SLA가 아니다.
- 서비스 내부 병목, 네트워크 비용과 통계적 유의성을 별도로 측정하지 않았고 실제 트래픽이나 다른 환경으로 성능을 일반화하지 않는다.
