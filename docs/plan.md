# dropgate 구현 플랜 (7주 + 버퍼 1주, 2026-10-06 착수)

기술 실험용 B2C 한정판 드롭 플랫폼. 사업성은 보지 않는다. 목적은 아래 일곱 기술을 측정 수치와 함께 코드로 남기는 것이다. 설계는 `docs/design/`에 먼저 확정했고, 이 플랜은 그 설계를 구현 순서로 나눈 것이다.

## 1. 대상 기술과 역할

| 기술 | 이 프로젝트에서 |
|---|---|
| Kotlin | 서비스 셋과 배치 전부 |
| Kubernetes | Deployment 3개, CronJob, HPA, PDB, 롤링 배포 실측. kind에서 EKS로 |
| Redis | 접속 대기열(정렬 집합), 재고 원자 차감(Lua), 1인 1회, 토큰 무효화, Streams 이벤트 채널, Sentinel 고가용성 |
| MSA | 서비스 셋, outbox, 멱등 소비, 취소 보상. 비동기 경계는 주문에서 알림으로 하나 |
| NoSQL | DynamoDB 알림 피드, 조건부 쓰기 멱등 |
| 배치 | Spring Batch 결산과 대조, 100만 건, 재시작 |
| 인증 인가 | 카카오 OAuth2, JWT RS256, JWKS로 분산 검증, 로그아웃 즉시 무효화 |

Kafka 대신 Redis Streams를 쓴다. Redis가 이미 있어 스택이 늘지 않고, Kafka와의 차이는 ADR 0008에 적는다.

## 2. 측정으로 답하는 질문 (README 상단 표가 된다)

| 기술 | 질문 | 측정 | 합격 |
|---|---|---|---|
| Redis | 재고 100개에 1만 요청을 파드 3개로 쏘면 성공이 정확히 100건인가 | k6 가상 사용자 500 | 초과 0, 중복 0 |
| Redis | Redis 재고와 DB 주문 수가 끝나고 일치하는가 | 대조 스크립트와 대조 배치 | 차 0 |
| Redis | 1만 명이 동시에 대기열에 들어와도 순번이 정확하고 초당 입장 수가 설정값을 지키는가 | k6 1만 가상 사용자 | 순번 역전 0, 입장 속도 오차 기록 |
| Redis | 대기열 전과 후에 주문 서비스 스파이크 p99가 어떻게 달라지는가 | 같은 스파이크를 대기열 끄고 켜고 | 전후 수치 |
| Redis | 마스터를 죽이면 절체까지 몇 초, 그동안 거절 몇 건, 절체 뒤 대조 차는 | Sentinel 마스터 종료 | 초, 거절 수, 대조 차 |
| Redis | Redis 전체가 죽으면 판매를 막는가 | Redis 전부 종료 중 요청 | 막는 정책대로, 초과 0 |
| MSA | 주문 1만 건에 알림이 정확히 1만 건인가 | Streams 소비 뒤 DynamoDB 건수 | 유실 0, 중복 0 |
| MSA | 알림 서비스를 죽였다 살려도 결과가 같은가 | 소비 중 파드 종료 뒤 재개 | 유실 0, 중복 0, 회복 초 |
| MSA | 주문 취소 시 재고가 정확히 복구되는가 | 취소 1,000건 뒤 대조 | 차 0 |
| NoSQL | 사용자 피드 조회 p99와 쓰기 1만 건 시간 | k6, PostgreSQL JSONB와 한 줄 비교 | 수치 기록 |
| 배치 | 100만 건 결산 처리 시간, 청크 크기 전후 | 청크 100, 1,000, 10,000 | 수치 기록 |
| 배치 | 50만 건에서 강제 실패 뒤 재시작하면 중복이 없는가 | 실패 주입 뒤 재실행 | 중복 0, 누락 0 |
| K8s | 부하 중 롤링 배포에서 오류가 나는가 | k6 중 배포 10회 | 5xx 0, 연결 거절 0 |
| K8s | 파드를 죽이면 몇 초에 회복하는가, HPA는 몇 개까지 느는가 | 파드 삭제, 스파이크 0에서 1,000 요청/초 30초 | 회복 초, 확장 수, p99 |
| K8s | CronJob이 정시에 돌고 실패 시 재시도하는가 | 배치 CronJob 관찰 | 실행 기록 |
| 인증 | 로그아웃 토큰이 세 서비스 전부에서 거절되는 시간 | 로그아웃 직후 서비스별 요청 | 측정값, 목표 100ms 안 |

합격이 아니라 측정이 목표다. 나쁜 수치도 전후 비교만 있으면 기록한다.

## 3. 주차 계획

### 사전 준비 (10-04에서 10-05)
레포와 모듈 뼈대(auth, order, notification, batch, common), README 뼈대, ADR 0001에서 0004, 카카오 개발자 앱 등록.

### 1주 (10-06에서 10-12) Kotlin 뼈대, 인증, DB만으로 구매
- 인증 서비스: 카카오 OAuth2, 사용자 저장, JWT RS256 15분, JWKS
- 주문 서비스: JWKS 자체 검증, 드롭 등록, DB만으로 구매와 확정(remaining_quantity UPDATE, UNIQUE로 1인 1회), 원장 불변 트리거와 제약 테스트
- Testcontainers PostgreSQL, ktlint, GitHub Actions CI
- 측정: DB만으로 서비스 1개에서 재고 100개 1만 요청 정확도와 p99(기준선)
- ADR 0005

### 2주 (10-13에서 10-19) Redis와 outbox
- 재고 차감 Lua, 1인 1회, 토큰 무효화와 리프레시, Redis 전체 장애 정책(막기) 테스트 고정
- outbox 테이블과 릴레이, Redis Streams 발행, 대조 스크립트
- 측정: 기준선 대 Redis 전후
- ADR 0006, 0007, 0008

### 3주 (10-20에서 10-26) 접속 대기열과 Redis 고가용성
- 대기열 진입, 순번 조회, 입장 스케줄러(초당 N명, 락), 입장 키 TTL 60초, 포기와 만료
- Sentinel 로컬 구성(마스터 1, 복제 2, 센티넬 3), 마스터 종료 실험
- 측정: 1만 명 순번 정확도와 입장 속도, 대기열 전후 스파이크 p99, 절체 초와 거절 수와 대조 차
- ADR 0009, 0010

### 4주 (10-27에서 11-02) 알림 서비스와 비동기 경계
- Streams 소비자 그룹, 멱등(DynamoDB 조건부 쓰기), XCLAIM, DLQ
- DynamoDB 테이블과 피드 조회(커서), 주문 취소 보상
- 측정: 주문 1만 대 알림 1만, 소비자 종료 뒤 회복, 취소 1,000건 대조, 피드 p99
- ADR 0011, 0012

### 5주 (11-03에서 11-09) 결산 배치
- Spring Batch 결산 잡과 대조 잡, 합성 100만 건, 재시작 실험, 청크 크기 비교, 인덱스 전후 EXPLAIN ANALYZE
- ADR 0013

### 6주 (11-10에서 11-16) kind 로컬 Kubernetes
- Deployment 3개, CronJob, Redis Sentinel 차트, DynamoDB Local, Ingress, Secret, 프로브, 자원 상한, HPA, PDB
- 실험: 파드 3개 정확도, 롤링 배포 10회, 파드 종료 회복, Redis 마스터 종료, 알림 파드 종료 뒤 재개, CronJob, 토큰 거절 시간
- ADR 0014

### 7주 (11-17에서 11-23) EKS와 운영 실측
- Terraform: VPC, EKS, RDS, ElastiCache Multi-AZ, DynamoDB, ECR, IRSA. Helm 배포, GitHub Actions CD, kube-prometheus-stack
- 실험: 스파이크에서 대기열 켜고 끈 p99와 HPA, 노드 drain, ElastiCache 장애 조치
- README 수치 표, 한계(모의 결제, 단일 리전, 합성 부하), terraform destroy
- ADR 0015, 0016

### 8주 (11-24에서 11-29) 버퍼
밀린 것을 끝낸다. 남으면 DB 경로 폴백을 붙여 막기 정책과 수치를 비교하거나 Redis Streams를 Kafka로 바꾸는 리팩터를 시작한다.

## 4. ADR 목록

0001 Kotlin, 0002 서비스 셋으로 나눈 이유와 경계, 0003 인증 방식, 0004 배포 경로(kind 먼저 EKS 나중), 0005 DB만으로 먼저, 0006 Redis 전체 장애 정책(막기), 0007 Lua 대 분산 락, 0008 outbox 대 직접 발행과 Streams 대 Kafka, 0009 접속 대기열 설계, 0010 Sentinel과 절체 중 정합성, 0011 DynamoDB 대 PostgreSQL JSONB, 0012 멱등 소비와 DLQ, 0013 청크 크기와 재시작, 0014 프로브와 종료 유예, 0015 EKS 대 ECS, 0016 결과와 한계. 번복은 지우지 않고 superseded로 남긴다.

## 5. 비용 (추정)

7주 차 한 주 약 8.5만 원(EKS 컨트롤 플레인, t3.medium 3대, RDS micro, ElastiCache micro 2개, DynamoDB 온디맨드). 1에서 6주는 로컬이라 0원. 측정이 끝나면 바로 내린다.

## 6. 축소 순서

인증 서비스를 주문 서비스에 합침 -> DynamoDB를 PostgreSQL JSONB로 -> 대조 배치 생략 -> Sentinel을 단일 Redis로 -> EKS를 빼고 kind 결과로 마무리. 끝까지 두는 것: Kotlin, 대기열과 재고 정확도, 비동기 경계 하나, 배치 재시작, kind 파드 3개 실험, 테스트, CI, 측정 표, ADR.

## 7. 규칙

PR 300줄 이하. 테스트는 기능과 같은 PR. 주석 대신 이름과 테스트. 설계 변경은 docs/design/을 먼저 고치고 ADR에 이유. 수치는 재는 명령과 함께 적고 합성 부하임을 밝힌다.
