# 장애 중 보존과 복구 뒤 발행을 같은 시나리오로 고정한다

| 항목 | 내용 |
|---|---|
| 날짜, 도구 | 2026-10-19, Claude Code 자동 리뷰 제안(요약 댓글의 제안) |
| 제안 요지 | 연결 거절 때 attempts 보존과 다음 실행의 정상 발행을 별도 테스트로 나눈다. |
| 왜 틀렸나 | 과잉. 이 테스트는 장애 중 실패 한도를 소비하지 않은 미발행 행이 다음 실행에서 유실 없이 발행되는 복구 계약을 검증한다. 보존만 확인하면 다음 실행에서 선택되지 않는 회귀를 놓치고 복구만 확인하면 장애가 일반 실패 횟수를 소비하는 회귀를 놓친다. 같은 이벤트의 장애 전후를 이어 검증하는 편이 계약을 직접 보여 준다. |
| 어떻게 알았나 | 테스트. [리뷰 제안](https://github.com/moonino/dropgate/pull/142#issuecomment-6261092744)을 AGENTS.md의 같은 개념 다중 단언 허용과 04 문서의 네트워크 장애 정책에 대조했다. 실제 닫힌 포트로 발행한 뒤 attempts 0과 PENDING을 확인하고 같은 세 행을 정상 Redis로 발행했다. JDK 21의 `JAVA_TOOL_OPTIONS=-XX:ActiveProcessorCount=2 ./gradlew --max-workers=2 ktlintCheck :order-service:test`에서 order 193개가 통과했다. |
| 대신 한 것 | 연결 거절부터 다음 실행의 정상 발행까지 같은 이벤트를 사용하고 복구 흐름이 드러나는 이름을 유지한다. PR #142. |
